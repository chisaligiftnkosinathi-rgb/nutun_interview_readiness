## Q8.1: Retrieval-Augmented Generation (RAG) Architecture & Vector Similarity

### Question
> *"What is Retrieval-Augmented Generation (RAG), why would you use it instead of simply putting all the policies into the prompt or fine-tuning the model, and how does vector similarity actually help retrieve relevant information?"*

### Verified Candidate Answer

#### 1. What RAG Actually Is
**Retrieval-Augmented Generation (RAG)** is an architecture that decouples knowledge storage from the LLM’s parametric memory. Instead of relying solely on the model's pre-trained weights, RAG dynamically retrieves authoritative, domain-specific text snippets from an external knowledge base and injects them into the prompt context at query time.

The process consists of three distinct phases:
1. **Retrieval**: Querying an external database to fetch the top-$k$ most relevant text chunks.
2. **Context Construction**: Assembling the retrieved passages, system constraints, and agent question into a structured prompt.
3. **Generation**: The LLM synthesizes a grounded answer based strictly on the provided context passages.

---

#### 2. Why NOT Put Everything into the Prompt?
1. **Context Window Costs & Token Economics**: Loading thousands of compliance documents into every prompt consumes millions of tokens, making operational API costs unsustainable at 18.5M interactions/month.
2. **Latency (TTFT)**: Processing a 500,000-token prompt increases Time to First Token by several seconds, stalling live call-centre conversations.
3. **"Lost in the Middle" Degradation**: LLMs exhibit attention degradation over massive context windows, frequently missing critical policy clauses buried in the middle of long documents.
4. **Dynamic Policy Updates**: Financial policies update frequently. Re-indexing new documents takes seconds; sending static massive prompts cannot handle real-time revisions efficiently.

---

#### 3. Why NOT Simply Fine-Tune the Model?
1. **Knowledge vs. Behavior**: Fine-tuning is designed to adapt *tone, format, or specialized task behavior*—it is a poor mechanism for factual knowledge recall. Models still hallucinate factual details even when fine-tuned.
2. **Frequent Policy Churn**: Training/fine-tuning takes hours or days and substantial GPU compute. If Nutun revises a debt settlement threshold at 10:00 AM, fine-tuning cannot update the model before an agent takes a call at 10:05 AM.
3. **Auditability & Citations**: Fine-tuned weights are black boxes. A fine-tuned model cannot provide verifiable page-and-paragraph citations proving where a policy rule originated.
4. **Tenant Isolation**: A single fine-tuned model cannot safely segregate Bank A's private rules from Bank B's private rules without risking weight leakage.

---

#### 4. Embeddings & Vector Similarity Explained
An **embedding** is a dense numerical vector (e.g. an array of 1,536 floating-point numbers) generated by a specialized embedding model. It captures the **semantic meaning** of text in high-dimensional space:
* Phrases with similar conceptual meaning (e.g., *"debt forgiveness"* and *"settlement discount"*) are projected close together in vector space, even if they share zero identical words.
* **Vector Similarity (Cosine Similarity)** measures the cosine of the angle between two vectors:
  $$\text{Cosine Similarity} = \frac{\mathbf{A} \cdot \mathbf{B}}{\|\mathbf{A}\| \|\mathbf{B}\|}$$
  A score of `1.0` means identical direction (high semantic alignment); `0.0` means orthogonal (unrelated).

```text
       │

       │
       ▼

══════════════════════════════════════════════════════════════════════════════════
[ QUERY PHASE (Runtime) ]
Agent asks: "What is the policy for 2 missed instalments?"
       │
       ▼
1. Query Embedding (Converts user question to vector)
       │
       ▼
2. Vector Similarity Search + MANDATORY METADATA FILTERING:
   WHERE tenant_id == "BANK_A" AND active == true
       │
       ▼

       │
       ▼
4. Prompt Construction on Server:
   [System]: "Answer strictly using the provided policy excerpts. If uncertain, say 'No policy found'."
   [Context]: Chunk 1 (Policy AR-2026-17), Chunk 2 ...
   [Question]: Agent's question.
       │
       ▼
5. LLM Invocations & Streaming Grounded Response with Citations [1]
```

#### 6. The Critical Security Standard: Vector Similarity $\neq$ Authorization
> **"Vector similarity is a retrieval heuristic; it is NEVER an authorization boundary."**

You can never rely on the vector database to "naturally" return only the documents an agent is cleared to see. If an agent belongs to Bank A, the backend query MUST enforce a hard metadata filter at the database engine level:
```sql
-- Hard deterministic boundary, not a fuzzy semantic suggestion:
SELECT chunk_text, doc_id 
FROM policy_vectors 
WHERE tenant_id = 'BANK_A' 
  AND clearance_level <= :agent_clearance
ORDER BY vector <=> :query_vector 
LIMIT 5;
```
If a document does not belong to the authorized tenant, it must be excluded from the database search space before cosine similarity is ever computed.

### The Hostile Curveball Defense

> **Interviewer**: *"Suppose the customer asks for policy `AR-2026-17`. Your vector search returns a semantically similar policy, but the exact policy number isn't present in that document. Would you trust the vector result?"*

### Candidate Defense
*"No, absolutely not. I would **not** trust that vector result, and this illustrates the classic blind spot of pure vector retrieval:

#### 1. Why Vector Embeddings Fail on Exact Alphanumerics
Dense vector models compress language into semantic themes. An embedding understands the concept of *'debt rescheduling rules'*, but it treats specific alphanumeric tokens—like `AR-2026-17`, `Section 4.2(b)`, or South African ID numbers—as abstract tokens. Vector search will happily return `AR-2024-09` because its semantic text is 96% similar, completely ignoring that the user asked for a different legal document version.

#### 2. The Solution: Hybrid Search (BM25 Keyword Matching + Dense Vectors)
In an enterprise financial system, we never deploy pure vector search. We deploy **Hybrid Search**:
1. **Sparse Lexical Search (BM25 / Full-Text Search)**: Performs exact keyword matching on specific strings like `AR-2026-17` and account codes.
2. **Dense Semantic Search (Vectors)**: Captures conceptual intent and plain-language inquiries.
3. **Reciprocal Rank Fusion (RRF)**: Merges both result sets using a reciprocal rank algorithm:
   $$\text{RRF Score}(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$
4. **Cross-Encoder Re-Ranking**: A second-stage re-ranker evaluates the top 20 candidate passages to verify whether the query's exact identifiers match the retrieved chunks before they are sent to the LLM.

#### 3. Frontend Fallback Behavior
If hybrid retrieval still fails to locate policy `AR-2026-17`:
* The frontend suppresses generation.
* The UI displays an explicit fallback state: *"Policy AR-2026-17 could not be located in current guidelines. Please check the policy number or consult your team lead."*
* We never allow the model to guess or substitute an adjacent policy as truth."*
