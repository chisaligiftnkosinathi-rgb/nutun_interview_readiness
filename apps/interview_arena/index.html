FOUNDATION LESSON 01

The Anatomy of a Web Request

Governing Question: portal.nutun.com

When an agent opens a case file or an automated AI webhook triggers in Nutun's portal, the browser executes an intricate, distributed pipeline before a single component can render. Mastering this sequence prevents production misdiagnoses when APIs appear slow.

1. URL & DNS

Browser checks cache, OS resolver queries DNS to map hostname to an IP address.

2. TCP & TLS 1.3

3-way TCP handshake establishes byte stream; TLS 1.3 completes secure cryptographic keys.

3. HTTP & TTFB

Client sends HTTP GET/POST with headers; waits for first byte of response stream (TTFB).

4. Critical Path

HTML tokenized into DOM; CSSOM parsed (render-blocking); Layout and Paint occur.

⚡ Why DNS & Connection Caching Matters

DNS resolution can take 50–200ms on a cold cache. Browsers cache DNS records based on the server's Time-to-Live (TTL). TCP handshake takes 1 round-trip time (RTT); TLS 1.3 adds another 1 RTT.

With HTTP/2 connection keep-alive or HTTP/3 QUIC, subsequent API calls to Nutun microservices reuse existing connections, bypassing connection latency entirely.

🛑 Render-Blocking vs. Parser-Blocking

CSS is render-blocking: The browser refuses to render pixels until the CSSOM is constructed to avoid Flash of Unstyled Content (FOUC).

Synchronous JS is parser-blocking: When the HTML parser sees a traditional <script>, it stops building the DOM until the script downloads and executes. Use defer or type="module" to keep parsing non-blocking.
